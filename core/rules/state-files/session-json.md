# session.json — Multi-Task Session Registry

Session-level state for one `crew:run` invocation. Lives at
`${STATE_DIR}/session.json` (one file per project, not per task).
Written by `crew:run` Step 4 and mutated by Step 1.5 (task injection)
and Step 7 (result collection).

The session.json file is the canonical answer to "is there an active
crew:run for this project right now?" — both `crew:run` (for injection
detection) and `crew:status` (for session-aware mode) consult it on
every invocation.

## File Location

```
${STATE_DIR}/session.json
```

Where `STATE_DIR = ${AGENT_CREW_HOME}/state/${PROJECT_NAME}`. Wiped
by `crew:setup` reset; preserved across `crew:update`.

## Schema

Canonical shape (with Phase B0 `task_hash` field):

```json
{
  "schema_version": 1,
  "session_id":     "20260516-012345",
  "status":         "running",
  "pre_run_head":   "abc1234",
  "tasks": [
    {
      "task_id":   "20260516-012345-0",
      "task_dir":  "/path/to/.agent-crew/state/proj/tasks/20260516-012345-0",
      "branch":    "feat/implement-order-api",
      "task":      "implement order API",
      "task_hash": "implement order api",
      "status":    "running",
      "injected":  false
    }
  ]
}
```

JSON Schema: `${AGENT_CREW_HOME}/schemas/session.schema.json`. The
schema sets `additionalProperties: true` for both the top-level object
and each `tasks[]` entry because field set evolves per refactor phase.

### Field catalog (top-level)

| Field | Type | Required | Notes |
|---|---|---|---|
| `schema_version` | integer (const 1) | optional | Pre-F4 session.json files omit this; validator tolerates absence. |
| `session_id` | string | yes | Pattern `{YYYYMMDD}-{HHMMSS}`. Generated by Step 4 of the non-injecting orchestrator. |
| `status` | enum `running \| completed \| blocked` | yes | `running` = live session accepting injections; `completed` = closed by Step 7. |
| `pre_run_head` | string | optional | Git SHA of HEAD before any task spawned. Used by `crew:status --collect` for diff stat. |
| `tasks` | array | yes | One entry per task in the session, including injected. |

### Field catalog (each `tasks[]` entry)

| Field | Type | Required | Notes |
|---|---|---|---|
| `task_id` | string | yes | Pattern `{YYYYMMDD}-{HHMMSS}-{idx}`. |
| `task_dir` | string (absolute path) | yes | Used by Step 7 result collection. |
| `branch` | string | yes | Follows `core/rules/branch-naming.md`. |
| `task` | string | yes | Original task description. |
| `task_hash` | string | optional (Phase B0+) | Normalized form for duplicate-injection detection. Pre-B0 entries omit it. |
| `status` | enum `running \| completed \| blocked` | yes | Bumped to terminal value by Step 7 once `result.md` is parsed. |
| `injected` | boolean | optional (defaults to false) | True for tasks added by Step 1.5 injection path. |

See `core/rules/task-injection.md` § `task_hash` field for the
normalization algorithm.

## Lifecycle

### Created

`core/commands/run.md` Step 4: when starting a new non-trivial run, the
orchestrator writes the initial session.json with `status: running`
and one entry per task. Each entry's `task_hash` is computed via the
B0 normalization algorithm.

### Mutated

| Event | Field mutated |
|---|---|
| Step 1.5 task injection | append new entry to `tasks[]` with `injected: true` |
| Step 7 result collection | per-task `status` bumped to terminal value |
| Step 7 final | top-level `status` set to `completed` |
| Crash recovery (Step 7) | per-task `status` set to `blocked` after retry exhaustion |

## Concurrency

Both the original orchestrator and the injecting `crew:run` write to
the same session.json. The concurrency model is documented in
`core/rules/task-injection.md` § Concurrent Write Safety:

- All writes use a single `python3 -c` read-modify-rewrite cycle
  (not atomic, but the corruption window is microseconds).
- Writes are append-only (mutations are limited to status field
  bumps on existing entries + appends to `tasks[]`).
- Status-completed write fires only from the original orchestrator.

For MVP scope this is acceptable. A future stronger-guarantee phase
should adopt the same tempfile + rename pattern that `register_update`
introduces in F4.

## Consumer Contract

Primary consumers:

- `core/commands/run.md` Step 1.5 (injection detection) — checks
  `status == running` + file mtime ≤ 24h.
- `core/commands/run.md` Step 1.6 (duplicate-task detection) — compares
  new task's `task_hash` against every running entry's `task_hash`.
- `core/commands/status.md` Step 1c (session-aware mode detection) —
  same conditions as injection detection.
- `core/commands/status.md` Step 4S (collect mode) — polls `tasks[]`
  for terminal state.

| Situation | Behavior |
|---|---|
| File absent | No active session. Both `crew:run` and `crew:status` proceed in single-task mode. |
| File present, `status == running`, mtime ≤ 24h | Live session; injection path / session-aware mode applies. |
| File present, `status == running`, mtime > 24h | Stale session; treat as completed. |
| File present, `status == completed`/`blocked` | Closed session; `crew:status` may still render the table. |
| Required field missing (top-level) | Warn but continue; session-aware mode falls back. |
| Required field missing (one `tasks[]` entry) | Skip the entry; warn; render the rest. |
| `task_hash` missing (pre-B0 entry) | Duplicate detection treats as "cannot dedupe; assume unique". |
| Unknown top-level field | Forward-compat: tolerate. |

## Forward Compatibility

`additionalProperties: true` everywhere. F4 schema validator emits
warnings (not errors) for cross-task files — a single malformed entry
must not abort an entire run.
