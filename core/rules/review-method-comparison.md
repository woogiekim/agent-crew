# 리뷰 방법 비교와 트레이드오프

## 적용 범위

리뷰 보고서, 후속 처리 분석·계획·인계, 반영률 설명, MR 반영 노트, 사후 점검,
리뷰 회고와 계약 정합성 점검에서 방법 선택이나 대안 비교가 필요한 항목에 적용한다.
단순 발견사항, 반영률 수치, 다음 행동 메뉴에는 대안 비교를 억지로 만들지 않는다.
원문 리뷰·렌즈 결과·원시 증거·프로토콜 필드는 보존하고, 사용자에게 설명하는 부분에 적용한다.

## 작성 규칙

- 방법명은 실제 동작과 차이를 드러내는 구체적인 이름으로 쓴다. 예시의 알파벳·순번을
  방법명의 고정 접두어로 쓰지 않고, 후보 수도 실제 실행 가능한 방법에 맞춘다.
- 항목명 다음에 `<구체적인 방법명> — 채택` 또는 `— 권장`을 먼저 쓴다.
  실제 결정·반영 근거가 있는 경우만 `채택`, 제안 단계는 `권장`, 근거가 부족하면 `판단 보류`로 쓴다.
- 다른 후보보다 적합한 이유를 현재 계약·제약·근거에 연결해 1~2문장으로 설명한다.
  이어서 `얻는 점`과 `감수할 점`을 각각 짧은 개조식으로 쓴다.
- 이해득실 목록 뒤에 빈 줄, `#### 방법별 비교` 소제목, 다시 빈 줄을 두어 맥락 전환을 표시한다.
  항목 제목은 `###`로 쓴다. 상위 문서의 제목 깊이가 다르면 이 상대적 계층을 유지한다.
- 후보는 마크다운 번호 목록으로 쓴다. 각 방법을 1~2문장으로 설명한 뒤 빈 줄을 두고,
  들여쓴 `장점`·`단점` 목록을 쓴다. 후보 사이에도 빈 줄을 둔다. 선택한 방법도 포함한다.
- 정확성·호환성·성능·구현 비용·운영 비용·복잡도 중 실제 차이를 만드는 기준으로 비교한다.
  선택 요약은 결정의 핵심, 후보별 설명은 작동 방식과 차이를 담고 같은 문장을 반복하지 않는다.
- 근거가 있는 후보만 제시한다. 하나뿐이면 이유를 적고 비교용 대안을 만들지 않는다.
  확인한 사실은 `file:line`이나 현재 확인한 아티팩트로 뒷받침하고, 미확인 효과·비용은 명시한다.
- 마지막에 `확인 근거와 한계` 소제목을 두어 코드·결정·검증 근거와 미확인 사항을 구분한다.
  코드를 읽은 사실을 런타임·운영 검증으로 확대하지 않는다.
- 일반 발견사항의 줄 수 제한은 방법 비교 블록에 적용하지 않는다. 보고서 전체 제한을 넘으면
  우선순위가 높은 비교는 본문에 남기고 나머지 전체 비교는 허용된 로컬 아티팩트로 옮겨 연결한다.
  로컬 저장이 허용되지 않았으면 분할 출력한다. 설명을 한 줄로 압축하거나 장단점을 생략하지 않는다.

## 공통 형식

```markdown
### <리뷰 항목명>

<구체적인 문제·발생 조건·영향을 짧게 설명>.

**<선택한 구체적인 방법명> — <채택|권장|판단 보류>**

<현재 계약·제약에서 해당 방법을 선택한 이유 1~2문장. 보류라면 부족한 근거>.

- 얻는 점: <구체적 이익>.
- 감수할 점: <수용할 비용·제약·위험>.

#### 방법별 비교

1. **<비교 후보의 구체적인 방법명>**

   <무엇을 어떻게 하는 방법인지 1~2문장>.

   - 장점: <판단 기준에 따른 이점>.
   - 단점: <판단 기준에 따른 비용·제약>.

2. **<다른 비교 후보의 구체적인 방법명>**

   <무엇을 어떻게 하는 방법인지 1~2문장>.

   - 장점: <동일한 판단 기준에 따른 이점>.
   - 단점: <동일한 판단 기준에 따른 비용·제약>.

#### 확인 근거와 한계

<확인한 코드·결정·검증의 출처와 미확인 사항>.
```

번호 목록은 실제 후보 수만큼 작성한다. 위 두 후보는 구조 예시이며 고정 개수가 아니다.

## MR 노트와 상태·승인 경계

- 이미 확인된 반영 결정의 요약 노트에는 공통 형식을 적용하되, 로컬 반영과 원격 반영을 구분한다.
- `mr-review-note`는 방법 비교·확인 근거와 한계 뒤에 `검증 및 MR 상태` 소제목을 둔다.
  테스트·검사를 이번에 실행했는지 기존 결과만 확인했는지 명시하고, 로컬 반영·원격 MR 코드 반영·
  MR 설명 갱신·운영 검증을 각각 적는다. 근거가 없으면 미확인으로 표시하며 이 블록은 생략하지 않는다.
- 미결정 사항을 묻는 확인 노트에는 채택을 선언하거나 처리 방향을 강요하지 않는다.
  `판단 보류`와 필요한 근거를 적고, 방법별 설명·장단점 뒤에 중립적인 질문과 선택지를 둔다.
- 단순 처리 상태 확인 질문은 기존 질문·선택지 형식을 유지한다. 공통 형식은 방법 비교가 있을 때만 쓴다.
- 채택/권장은 구현 승인·실행 완료를 뜻하지 않는다. `candidate_disposition`, 반영 상태,
  반영률, 계약·범위·부작용 안전성, 잔여 위험을 별도로 보존한다.
- 부분 반영이나 기각은 장단점 설명만으로 완료가 되지 않는다. 원격 게시·수정은 기존대로
  최종 본문에 대한 명시 승인이 필요하다. 이 지침은 새 도구·실행 노드·쓰기 권한을 추가하지 않는다.

## 검증

- 실제 방법명과 실제 후보 수를 사용했는가.
- 선택 이유, 얻는 점·감수할 점, 방법별 설명·장단점이 있는가.
- 이해득실과 방법 비교 사이, 각 후보의 설명과 목록 사이에 빈 줄이 있는가.
- `방법별 비교` 및 `확인 근거와 한계` 소제목으로 맥락을 구분했는가.
- 단순 항목에 대안을 만들지 않았으며 근거·불확실성·반영 상태·승인 경계를 보존했는가.
