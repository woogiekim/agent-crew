# Review Evidence Style

MR !474 리뷰(ENRTC-1371)에서 효과가 확인된 진행 방식을 재사용 가능한 규칙으로 남긴다.
이 규칙은 아래 규칙을 **대체하지 않고 얹는다.** 같은 내용은 반복하지 않고 참조한다.

- 증거 등급, 부재 증명, caller graph: `core/rules/evidence-grounded-reasoning.md`
- 리뷰 코멘트 처분과 의도 보존: `core/rules/review-intent-fidelity.md`
- 계약 우선 판단: `core/rules/contract-first-feedback-fidelity.md`
- 렌즈 발견과 분류: `core/rules/review-lens-discovery.md`

이 규칙이 추가하는 것은 아래 5가지다.

## 1. 소스 브랜치는 체크아웃 없이 원격으로 읽는다

로컬 브랜치는 MR 의 전제(선행 MR 머지 등)를 담고 있지 않을 수 있다. 로컬 파일만 읽고
"없다"고 결론 내리지 않는다.

- MR 소스 브랜치 파일은 `glab api projects/<encoded-path>/repository/files/<encoded-file>/raw?ref=<encoded-branch>`
  로 읽는다. 저장은 scratchpad 에만 한다. 체크아웃, fetch, 로컬 ref 변경은 하지 않는다.
- 로컬 `HEAD` 가 MR 대상 브랜치와 어긋난 정황(선행 MR 의 심볼이 없음 등)이 보이면 보고서에
  "로컬 오래됨 가능, Unverified"로 적고, 원격 읽기로 확정하기 전에는 부재 결론에 쓰지 않는다.
- 원격 읽기로 앞선 서술이 틀렸음이 드러나면 **정정 항목**을 따로 적는다(§3).

## 2. 사실 · 추정 · 미확인을 문장 단위로 표시한다

- 코드를 읽어 확인한 것은 파일과 줄 번호를 붙여 단정한다.
- 라이브러리 동작 지식, 실행하지 않은 재현은 `Assumption:` 또는 `Unverified:` 를 붙인다.
- 보고서에는 항상 "확인한 것 / 확인하지 않은 것"을 분리한다. 테스트·브라우저를 실행하지 않았다면
  작성자 보고(예: MR 본문의 `117 pass`)를 "작성자 보고"로 적고 자신이 재현한 것처럼 쓰지 않는다.
- hunk 밖 코드를 읽지 못했으면 caller graph 는 `partial` 로 표시한다.

## 3. 의문은 확정 루프로 닫고, 앞선 보고서를 정정한다

1. 보고서의 `Unverified` 항목 중 판단을 좌우하는 것을 고른다.
2. 소스 브랜치의 정의·호출부를 읽어 사실로 확정하거나 반증한다.
3. 결과가 이전 서술과 다르면 "이전 보고서 정정" 문단으로 어떤 문장이 어떻게 바뀌었는지 밝힌다.
4. 확정 결과에 맞춰 이후 산출물(노트 초안)에서 해소된 질문을 **삭제**하고, 새로 드러난 사실만 추가한다.

## 4. 미결정 사항의 확인 노트에는 처리 방향을 넣지 않는다

리뷰 반영의 결정은 반영 담당자 몫이다. 아래 질문·선택지 제한은 미결정 사항을 묻는
확인 노트에 적용한다. 이미 확인된 반영 결정을 요약하는 `mr-review-note`에는
`core/rules/review-method-comparison.md`의 선택 이유·이해득실·방법별 비교 형식을 적용한다.
미결정 방법 비교는 `판단 보류`로 표시하고, 중립적인 질문과 선택지로 마무리한다.

- 확인 요청은 질문 한 줄과 선택지 목록으로 쓴다. "이렇게 고치세요"로 쓰지 않는다.
- 선택지에는 사실 기반 선택지(이미 처리됨 / 이 MR 에서 처리 / 후속 분리 / 현 상태 유지)를 균형 있게 둔다.
- 작성자가 이미 처리한 항목은 질문으로 남기지 않고, 확인한 사실로만 한 줄 적는다.

### 선택지는 마크다운 번호 목록으로 쓴다

- `1.` `2.` `3.` 번호 목록으로 쓰고, 한 선택지는 한 항목으로 둔다.
- `①②③` 같은 원문자를 쓰지 않는다. GitLab·GitHub 마크다운은 원문자를 목록 기호로 보지 않아
  줄바꿈이 무시되고 선택지 전체가 한 문단으로 붙어 식별이 어려워진다. 실제 게시물에서 확인된 현상이다.
- 목록 앞에는 빈 줄을 둔다. 빈 줄이 없으면 앞 문단에 흡수된다.
- 처리 상태 확인과 다음 행동 메뉴의 선택지 한 건은 한 줄(약 60자)로 끝낸다.
  방법 비교 후보는 공통 지침에 따라 설명·장단점과 빈 줄을 포함한다.
- 이 규칙은 **외부 마크다운으로 나가는 글**(MR 노트, 보고서 파일)에만 적용한다. 호스트 채팅창에서
  사용자에게 직접 묻는 선택지는 호스트의 응답 스타일 규칙을 그대로 따른다.

### 노트 한 건의 분량

- 단순 확인 노트는 근거 목록 + 질문 한 줄 + 선택지로 끝내고 서술 문단은 최대 2개로 둔다.
  방법 비교가 필요한 노트는 공통 형식을 적용하며, 2문단 제한으로 설명·장단점을 생략하지 않는다.
- 근거는 `file:line` 으로 쓴다. 같은 파일의 연속 줄은 한 항목으로 묶는다.
- 배경 설명, 선행 맥락, 다른 항목과 겹치는 내용은 반복하지 않는다.
- 미확인 한계는 노트 끝에 `Unverified:` 한 줄로 모은다. 문단마다 흩지 않는다.

## 5. 범위 밖 현상은 회귀와 분리해 non-blocking 으로 둔다

- 이 MR 이전부터 같은 동작이었음을 코드나 이력으로 설명할 수 있을 때만 "회귀 아님"이라 쓴다.
  실행해 보지 않았다면 `Assumption:` 을 붙인다.
- 별개 경로의 현상은 "참고 (non-blocking, 이 MR 범위 밖)" 에 두고, 이 MR 에서 다룰지 후속으로 둘지는
  작성자 판단에 맡긴다.
- 게시 가능한 노트에는 확인하지 못한 한계(재현 안 함, 미확인 경로)를 문장으로 남긴다.

## 쓰기 경계

- 노트 게시, MR 설명 수정, 커밋, push 는 사용자의 명시 승인 후에만 한다. 초안 작성과 게시는 별개 단계다.
- 승인은 초안 한 건에만 유효하다. 문구가 바뀌면 최종 초안을 다시 보여 주고 다시 승인받는다.
- 게시에는 `glab mr note create` 를 쓴다. `glab mr note --message` 는 deprecated 다.
- 한국어 본문은 heredoc 으로 파일에 쓴 뒤 읽어서 넘긴다. 유니코드 escape 를 쓰지 않는다.

## Checklist

- [ ] 소스 브랜치를 체크아웃 없이 원격으로 읽었는가 (또는 읽지 못한 이유를 적었는가)
- [ ] 로컬이 MR 전제를 담고 있는지 확인했는가
- [ ] 모든 단정에 파일·줄 근거가 있고, 나머지는 `Assumption:`/`Unverified:` 인가
- [ ] 판단을 좌우하는 `Unverified` 를 확정 루프로 닫았는가, 정정 문단을 남겼는가
- [ ] 미결정 확인 노트가 처리 방향을 강요하지 않고, 반영 요약은 실제 결정 근거를 담았는가
- [ ] 선택지를 `1.` 번호 목록으로 썼는가 (원문자 미사용, 목록 앞 빈 줄 있음)
- [ ] 단순 확인 노트는 서술 2문단 이내이며, 방법 비교 노트는 공통 형식을 지켰는가
- [ ] 회귀 여부와 범위 밖 현상을 분리했는가
- [ ] 게시 전에 최종 초안으로 명시 승인을 받았는가
