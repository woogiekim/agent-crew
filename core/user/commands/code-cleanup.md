# crew:code-cleanup — 주석·데드코드·import 정리와 테스트 보강

## 목적과 실행 조건
- 사용자가 이 커맨드를 명시적으로 호출한 경우에만 실행한다.
- 코드의 공개 계약과 정상 동작을 보존하며 불필요한 주석, 누락된 설명, 데드코드, unused imports, 테스트 공백을 정리한다.
- 분석만 요청하면 수정 없이 결과를 보고한다. 생성 파일, 외부 의존 소스, 사용자 제외 경로는 건너뛴다.
- 이 커맨드 자체를 만드는 요청은 대상 프로젝트 정리 실행을 의미하지 않는다.

## 입력
- 사용자 원문을 Root Input Snapshot으로 보존한다.
- PROJECT_ROOT: 명시한 저장소 또는 현재 작업 루트.
- SCOPE: 명시한 파일·모듈·커밋 범위. 생략하면 현재 staged/unstaged 변경 파일과 untracked 소스·테스트 파일을 후보로 삼는다. 민감 파일은 읽거나 포함하지 않는다.
- 변경 파일이 없고 범위를 지정하지 않았다면 구조화 선택 UI로 범위를 받는다. 저장소 전체를 자동 선택하지 않는다.
- 기존 테스트·검증 명령, 제외 경로, 분석 전용 여부를 확인한다.
- 기존 TASK_DIR가 있으면 참고한다. 별도 실행 상태 디렉터리는 필수가 아니다.

## 도구와 권한
- 로컬 파일 읽기·수정, rg, Git 읽기, 프로젝트의 formatter·정적 분석·테스트 도구를 사용한다.
- 기존 사용자 변경을 보존한다. reset, checkout, clean으로 변경을 지우지 않는다.
- 새 의존성, 전역 도구 설치, 네트워크 접근이 필요하면 이유와 영향을 먼저 알리고 적용 가능한 승인 규칙을 따른다.
- commit, push, MR/PR 생성, 외부 댓글, 배포는 이 커맨드 범위에 포함하지 않는다.
- crew:run 또는 crew:agent를 자동 호출하거나 숨겨진 Agent 실행을 시작하지 않는다. 사용자가 해당 진입점을 명시했다면 그 실행 계획과 권한을 따른다.

## 절차
1. 적용되는 AGENTS.md와 프로젝트 검증 규칙을 읽고 Git 상태를 확인한다. 대상 파일과 직접 연관된 테스트를 확정한다.
2. 아래 다섯 항목을 조사하고 모든 후보를 `삭제`, `유지`, `보류` 중 하나로 분류한다. 후보의 이름, 근거, 간접 사용 가능성을 기록하며 불확실한 후보는 수정하지 않는다.
   - 불필요 주석: 코드를 그대로 반복하는 설명, 오래되어 틀린 설명, 사용하지 않는 주석 처리 코드를 정리한다. 라이선스·저작권·생성 지시·도구 suppression·이슈 근거가 있는 TODO는 의미를 확인하지 않고 삭제하지 않는다.
   - 주석 보강: 코드만으로 알기 어려운 도메인 정책, 계약, 경계 조건, 호환성 사유, 부작용을 설명한다. 추측을 사실로 쓰지 않고, 변경한 API의 KDoc/Javadoc은 실제 계약과 맞춘다. 일반적인 given/when/then 구획 주석은 추가하지 않는다.
   - 데드코드: 각 심볼의 exact reference를 검색하되 직접 참조 없음만으로 데드코드로 판정하지 않는다. DI, reflection, JavaBean/Jackson/JSP EL/SpEL, serialization, GraphQL, ORM·MyBatis, 설정, 스케줄러, 플러그인, 프록시·AOP, 인터페이스·상속, 외부 모듈과 공개 API 호출 가능성을 확인한다. 데이터 키 문자열 참조와 메서드 호출 참조를 구분한다. 간접 사용 가능성을 배제하지 못하면 `보류`로 분류한다.
   - unused imports: 프로젝트 formatter·compiler·lint의 판단을 사용한다. wildcard, 확장 함수, alias와 연산자 해석을 확인하며 정규식 일괄 삭제를 피한다.
   - 테스트 보강: 누락된 정책·오류·경계·회귀 동작을 기존 테스트에서 찾는다. 구현을 복제하거나 단순 주석/import 변경만을 검증하는 테스트는 만들지 않는다. 테스트를 통과시키려고 기존 assertion을 약화하지 않는다.
3. 승인된 범위의 최소 변경을 수행한다. 관련 없는 포맷 변경이나 아키텍처 변경을 섞지 않는다. 코드의 설정·검증·변환·부작용·반환 맥락이 바뀌면 빈 줄로 구분한다.
4. 버그나 동작 변경이 필요한 문제가 발견되면 정리와 구분한다. 요청 범위를 벗어나는 계약·정책 변경은 먼저 결정받는다. 버그 수정을 진행하는 경우 재현 테스트 실패 → 최소 수정 → 성공 → 리팩터 검토 순서를 따른다. 동작 보존 정리의 특성상 실패 테스트가 필요하지 않은 경우에는 기존 동작 검증으로 근거를 남긴다.
5. 변경한 테스트와 관련 회귀 테스트, 변경 모듈 formatter·lint·compile 및 프로젝트 필수 검증을 수행한다. 캐시와 offline 실행을 우선한다. 마지막 코드 수정 후 관련 검증을 다시 실행한다. 기존 실패와 이번 변경 실패를 구분하고 실행 불가 원인을 명시한다.
6. 최종 diff에서 범위·의도치 않은 동작 변경·사용자 변경 보존·공개 계약·누락된 호출자를 검토한다. git diff --check 및 Git 상태로 산출물을 확인한다.
7. 최종 보고 전에 후보 분류표를 다시 확인한다. `보류` 후보가 하나라도 있으면 대상과 이유를 `DEFERRED`에 모두 기록한다. 보류 후보가 있는데 `DEFERRED: 없음`으로 보고하거나, 근거 없이 "데드코드가 없다"고 단정하지 않는다.

## 산출물과 완료 조건
- 대상 소스·테스트·필요한 인접 문서만 수정한다. 별도 보고서 파일은 요청되거나 기존 TASK_DIR에서 요구하는 경우에만 작성한다.
- 항목별 변경 내용, 파일 경로, 실제 실행한 검증과 결과, 보류한 후보 및 이유를 한국어로 간결히 보고한다.
- 확인하지 못한 사용 여부를 데드코드로 단정하지 않는다. 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 필수 검증을 수행하지 못했다면 completed로 표시하지 않고 blocked 사유를 보고한다.

```text
STATUS: <completed|blocked|cancelled>
FILES: <변경 파일 또는 없음>
VERIFY: <실제 실행한 검증과 결과>
DEFERRED: <모든 보류 후보와 이유 또는 없음>
```
